必须写明以下不变量：

- 同一物体只锁存一次识别结果。
- 同一轮最多发出一个机械臂请求。
- 非目标轮绝不动作。
- 新帧不得覆盖已锁存轮次结果。
- 超时、放弃和复位均有明确出口。

#### 3.2.4 参数与结果语义

说明目标颜色、任务模式、参考尺寸、阈值页、错误码和理由码的管理方式。

目标配置采用6位拨码逻辑编码，配置由板上CPU在开始事件到来时一次性锁存；形状目标固定为正方体，不额外占用拨码位。系统不设置任务一至任务四的完整编号，只保留区分两种尺寸关系所必需的1位模式：

| 逻辑位 | 字段 | 建议编码 |
|---|---|---|
| `CFG[0]` | 尺寸关系模式 | 尺寸关闭时忽略；尺寸启用时，`0`表示边长差恰为1 cm，`1`表示边长差不超过0.5 cm |
| `CFG[3:1]` | 目标颜色 | `000`白，`001`黑，`010`红，`011`蓝，`100`黄；所有任务均参与目标判定，其余编码无效 |
| `CFG[5:4]` | 尺寸条件 | `00`不考虑尺寸，`01`选择2.0 cm，`10`选择3.0 cm，`11`保留并判为无效配置 |

CPU每轮均识别并输出颜色、形状和尺寸。所有任务均启用目标颜色拨码并要求识别颜色匹配；目标形状固定为正方体，因此不设置形状拨码，识别为圆柱体或锥体时明确输出不抓取及形状不匹配原因。任务一、任务二的判定规则相同，无需在系统中区分：将尺寸条件置`00`即可，尺寸关系模式位被忽略。任务三、任务四将尺寸条件拨为2 cm或3 cm，并分别用尺寸关系模式`0/1`选择“差值恰为1 cm”或“差值不超过0.5 cm”。尺寸条件为`11`时拒绝启动并显示“尺寸配置无效”。2.5 cm是系统需要识别的物块尺寸，不是参考/目标配置选项，因此不占用拨码编码。

另选择两个经板级确认可用的按键作为`START`和`END`。每个物体放置完成后，操作员按一次`START`；CPU只响应消抖后的按下边沿，在该边沿原子锁存6位配置并启动本轮。按键持续按住不得重复启动，轮次执行期间的新`START`边沿不得覆盖已锁存配置。识别、判断及目标抓取/非目标跳过完成后，系统进入`WAIT_END`，操作员按一次`END`确认本轮结束；CPU随后请求机械臂返回固定安全位，等待到位稳定窗口后清除本轮结果和锁存，才进入下一轮`WAIT_PLACE`。非目标物由操作员人工移走，文档不规定移走动作与`END`按键的先后顺序。`END`在动作未完成、通信故障或安全互锁未满足时不得强制跳过故障状态。物理`SWx/KEYx`编号、有效电平、消抖周期、管脚和寄存器地址必须由同批次XML/peri.xml/SDC/BSP确认，正文在未冻结前只画逻辑接口，不填写猜测编号。

证据入口：CPU分类器、task matcher、round controller、competition transaction及其Host测试。

### 3.4 芯机接口、CDC与可解释OSD

本章按完整芯机协同接口方案展开，说明接口选择、原子快照、配置提交和可解释OSD的实现机制。叙述重点是契约与代码落点，不插入集成困难说明。

#### 3.4.1 APB轻量寄存器接口

说明为何低速配置和统计快照使用APB，而不是让CPU读取整帧或引入复杂AXI突发。

寄存器按三类组织：`feature_regs`、`result_regs`、`control_regs`。基址必须来自同批次 `soc.h`，正文以偏移和语义为主。

#### 3.4.2 帧级原子快照

这是创新点二的第一部分：

- FPGA在帧边界锁存完整特征。
- CPU按 `status/frame_id -> 特征组 -> status/frame_id` 双读规则取得一致快照。
- CPU用匹配的 `frame_id` ACK；陈旧ACK不能清除新快照。

#### 3.4.3 配置原子提交

这是创新点二的第二部分：

- CPU先写 staging 区。
- 写 `CFG_COMMIT(config_seq)` 表示完整配置已准备好。
- 像素域只在VSYNC边界切换 active shadow。
- `CFG_STATUS`回报 active/pending序号，避免半新半旧阈值和ROI。

#### 3.4.4 可解释OSD

OSD采用完整字段集：当前判定模式、轮次、拨码目标颜色、参考/目标尺寸、识别颜色、识别形状、识别尺寸、目标/非目标、抓取/不抓取、理由、机械臂状态和错误码。当前判定模式不强制显示“任务1/2/3/4”，而按配置解释为“颜色+正方体”“尺寸差=1 cm”或“尺寸差<=0.5 cm”；任务一与任务二无需系统区分。CPU产生全部语义，FPGA负责像素渲染。完整版重点说明结果语义、寄存器字段、原子提交和像素渲染流程；真实画面只使用已有原始素材，设计版式必须明确标注为“OSD设计示意”。

建议图表：APB窗口图、snapshot/ACK时序、staging/commit/active时序、OSD版式草图。

## 7. 第5章 总结与展望（1页）

### 5.1 三项核心创新归纳

#### 创新一：无DDR、无回压的双像素旁路视觉特征提取

问题：CPU读取完整图像带宽高，旁路模块若参与握手可能干扰显示主链路。

方法：2PPC只读tap在流上累计ROI统计，帧边界锁存低带宽特征。

落点：`feature_stats_tap`、ROI/feature contract。

证据：RTL/构建/后续板级快照验证分层列出。

#### 创新二：双原子协议保障的FPGA-RISC-V芯机协同

问题：跨时钟域多位特征和多寄存器配置容易出现撕裂与半更新。

方法：`frame_id + valid/ACK`原子快照，以及`staging -> commit -> active`帧边界原子配置。

落点：APB寄存器契约、CDC规则和CPU board I/O。

价值：在保持FPGA并行处理能力的同时，使CPU能够安全、灵活地调整规则和参数。

#### 创新三：面向评分链的一轮一事务可解释安全闭环

问题：连续视频帧可能重复触发机械臂，且评委要求每轮输出识别、判断、动作及理由。

方法：逐轮锁存、唯一动作请求、SKIP理由、OSD语义、单请求机械臂事务和fail-closed故障收敛。

落点：round controller、transaction、result semantics、OSD和arm controller。

价值：将比赛评分链直接落实为可审计的系统行为。

### 5.2 总结与展望

总结采用“四项核心成果 + 系统价值”的结构，完整版不列困难或未完成项：

1. 已实现并运行摄像头到HDMI视频输出。
2. 已形成FPGA ROI/双像素特征提取代码与验证入口。
3. 已形成CPU识别判断、四任务匹配和逐轮事务代码与Host证据。
4. 已形成myCobot协议、事务和动作控制代码，并具备机械臂独立工作现象。
5. 总结FPGA并行视觉、CPU灵活决策、可解释输出与安全动作事务构成的芯机协同价值。

## 11. 内部写作与事实核查备注（不得进入完整版技术文档）

### 11.1 已遇到的主要工程困难

0. **任务规则口径曾出现冲突，已按0715修正版校准**
   - 早期讨论曾将“颜色条件”理解为四项任务均参与目标判定。
   - 0715修正版第3-4页明确：任务一、二按指定颜色正方体判定；任务三、四正文只明确正方体尺寸关系。第5页要求各任务每轮均识别颜色、形状、尺寸，但“必须识别输出”不自动等于“每个属性都参与目标判定”。
   - 团队最终要求四项任务均使用颜色拨码参与判断，因此当前系统真值规则为：任务一、二判颜色+正方体；任务三、四判颜色+正方体+尺寸关系。该规则比0715正文对任务三、四的显式条件更严格，提交前需结合现场配置口径复核，避免漏抓官方尺寸目标。

1. **FPGA与片上CPU的真实连接未完成板级闭环**
   - FPGA侧已有ROI、双像素特征累计、帧边界快照等RTL代码。
   - CPU侧已有稳定快照读取、`frame_id`二次校验、ACK、分类和任务判断代码。
   - 当前缺少同一硬件批次上的CPU取指、APB/MMIO真实读取及连续帧快照证据，因此不能把两侧代码存在写成FPGA-CPU链路已验证。

2. **CPU结果到OSD的硬件回写未完成板级验证**
   - CPU侧已有颜色、形状、尺寸、动作、bbox和OSD控制字段的staging写入代码。
   - FPGA侧OSD职责与结果语义契约已经明确。
   - 当前没有匹配批次的CPU回写后HDMI显示实拍，完整版只能展示OSD版式、寄存器契约和代码结构，不能伪造实测画面。

3. **机械臂已由PC完成独立抓取，但板上CPU到机械臂的真实后端尚未接入**
   - PC侧已有`pymycobot`示教、抓取与180度动作调试材料，可作为“机械臂独立抓取验证”。
   - 板上CPU侧已有myCobot协议封包/解析、事务层、动作状态机、超时、有限重试和安全互锁代码。
   - 当前`arm_runtime`只有模拟后端能够接受动作请求；非模拟后端保持拒绝请求，真实UART2/J52传输后端尚未接入或启用。
   - 因此不能把PC抓取照片标为FPGA识别自动触发，也不能声称板上CPU已控制机械臂完成抓取。

4. **端到端自动闭环无法验证的直接原因与实现边界**
   - FPGA-CPU APB/MMIO链路未验证，使真实视觉特征无法进入板上分类与逐轮事务。
   - CPU-OSD实际回写与CPU-myCobot真实UART2后端尚未形成同批次硬件链路。
   - 虽然视觉特征、分类判断、唯一动作请求、机械臂协议和动作控制各层代码均已形成，但代码存在只支持“完整设计具备实现基础”，不能替代端到端实测结论。

### 11.2 项目实施困难

- FPGA、SoC XML/peri.xml/SDC/IP/顶层/BSP/APB属于原子硬件批次，任一输入变化都会使旧构建与板级证据失效，导致联调窗口被进一步压缩。
- FPGA、CPU和机械臂并行开发时，Host、RTL仿真、Efinity构建、PC实机与板级闭环证据层级不同，整合时需要逐项核对，不能相互外推。
- UART0 Hello为115200，myCobot正式链路为1000000；两条链路的硬件、电气和软件Gate相互独立，基础CPU启动通过也不能直接授权机械臂接线与动作。
- 截止时间紧，最终文档必须优先保证架构、代码和已有证据准确，不以虚构数据弥补板级测试窗口不足。
