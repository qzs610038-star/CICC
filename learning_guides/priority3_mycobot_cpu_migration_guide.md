# 学习指南：myCobot 机械臂 CPU 控制逻辑迁移设计

> **前言**：本指南基于 `priority3_mycobot_cpu_migration_design.md` 编写，旨在帮助您全面理解如何将 PC 端的机械臂控制代码（Python）安全、规范地迁移到开发板的 RISC-V CPU（C语言）中。

## 1. 为什么要迁移？（决策依据）
在开发初期，我们使用 PC 和 Python (`pymycobot`) 脚本来控制机械臂，这非常适合标定点位和验证安全门限。但根据《分赛区决赛实施开发路线》的**硬边界约束**：
*   **最终控制闭环必须在板上 CPU 中完成**：PC 仅仅是开发期的调试工具。
*   **FPGA 与 CPU 的分工**：FPGA 负责视频流和特征提取；开发板上的 CPU 必须承担起“识别决策、参数管理、以及直接向机械臂发送 UART 控制协议”的重任。

## 2. 目前开发板 CPU 代码处于什么阶段？
简单来说，目前 C 语言代码里跟机械臂相关的 4 个关键文件**全都是“空壳子”**，没有任何实质的控制能力：
*   `arm_controller.c`：目前只定义了一个空的结构体，缺少核心的状态机、命令下发和定时器轮询逻辑。
*   `mycobot_protocol.c`：目前发包函数是个半成品，不仅丢弃了实际的 payload（有效载荷），而且完全没有写“如何解析机械臂返回的数据包”。
*   `arm_positions.h`：目前只有一个安全位置声明，缺少抓取流程所需的起、抓、落、放、回零等 5 个关键点位数据。

## 3. 从 PC 端迁移哪些核心逻辑？
我们在 PC 端经过了几十次 Trial Run（试运行）打磨出的稳健逻辑，必须原封不动地搬到 C 语言中：
*   **非阻塞的软到位轮询**：CPU 不能发了命令后死等（死等会卡死整个系统），必须用定时器每隔 50-100ms 问一下机械臂“你到了吗”。
*   **严密的异常处理（三段式重试）**：如果机械臂迟迟没到位（软超时），CPU 不应该立刻崩溃报错。它需要：
    1. 读一下当前真实坐标，如果在误差容忍度内，算作“勉强通过”。
    2. 如果误差较大，用极慢的速度把同样的目标点再发一次（有界重试）。
    3. 如果还是失败，才真正抛出严重错误（熔断）。
*   **安全防掉落机制**：如果在机械臂悬空或者抓着重物时发生错误，不要立刻切断舵机电源（Release），否则机械臂会直接砸下来。要保持扭矩，等待人工救援。

*(注：不需要迁移 PC 端的控制台交互提示、本地日志保存，以及无限循环抓取的逻辑，开发板上应遵循“识别一次，抓取一次”的单次事务设计。)*

## 4. 迁移时的 C 语言模块分工
为了代码清晰，必须严格分层：
1.  **协议层 (`mycobot_protocol.c`)**：只做翻译官。它负责把指令变成字节流（如 `0xFE 0xFE 长度 命令...`），并从串口读到的乱码中提取出有效的当前角度。它绝对不能包含任何抓取流程的逻辑。
2.  **点位库 (`arm_positions.h`)**：静态的数据仓库，存放每个动作的角度、速度和安全检测半径。
3.  **核心主脑 (`arm_controller.c`)**：整个流程的总指挥。它提供如“初始化”、“请求抓取”、“定时推进 (Tick)”等 API，内部通过一个大的状态机（空闲 -> 移动到上方 -> 抓取 -> 抬起 -> 移动到目标框 -> 放下 -> 回归准备位）来完成任务。

## 5. 安全第一：分四批次实施（步步为营）
为了绝对安全，代码的编写和上板测试必须分为四步，**前三步都绝对不能让机械臂动起来**：
*   **第一批（纯写协议，不动机械臂）**：写好拼包和解包的函数，通过单元测试验证解析乱码和错包的能力。
*   **第二批（纯写逻辑，不动机械臂）**：写状态机和超时逻辑，用代码模拟机械臂的回复，测试超时报错机制是否正确。
*   **第三批（只读不写，插线测试）**：接上真实的 UART2 线缆，CPU 只向机械臂请求“当前角度”，验证通信是否畅通。
*   **第四批（终极动车，慢速测试）**：通过前面所有的审查后，只发一条极慢速的回零指令。只有慢速回零完美成功，才能最终放开抓取序列的封印。
