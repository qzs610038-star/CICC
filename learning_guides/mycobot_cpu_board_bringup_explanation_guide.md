## 1. 核心专有名词“大白话”拆解

为了让非主责开发的队员也能快速听懂调试进度，我们将这套复杂的上板方案用最直白的语言进行拆解：

*   **正交维度构建 (Orthogonal Build)**：不要把“运行哪个程序”和“机械臂怎么控制”混为一谈。我们现在将它们拆成两条独立的轨道——**应用入口（我们跑哪个程序）**和**控制后端（我们用哪种方式控制机械臂）**。拼乐高时，你可以选择拼成“跑车”还是“飞机”（应用入口），同时这辆跑车可以用“手动拉着走”、“装上发条”或者“装上真实的马达”（控制后端）。
*   **动作无 ACK 协议 (No-ACK Protocol)**：机械臂是个“哑巴”。你发短信命令它“向前走”，它收到并执行了，但**绝对不会**给你回个“收到”。这就是无 ACK（无应答）。如果你的程序因为没收到 ACK 就一直等，就会直接死锁；或者误以为只要“短信发出去”（TX成功）就等于机械臂“已经走到了”，也会导致整个业务错乱。
*   **编译 section 被回收 (Symbol Garbage Collection)**：编译器非常聪明，在生成芯片能运行的程序时，它会把“看起来从来没被调用的代码”当成垃圾直接扫地出门（gc-sections 优化）。如果我们的测试工程里有一部分代码没被调用，链接器就会把它们删掉，这就导致生成出来的最终程序里缺了关键功能。
*   **ENTRY 链接警告 (Linker Warning)**：程序在芯片里启动时需要一个准确的“入场口”。链接脚本要求入场口叫 `_startup`，而启动汇编却只在大门口挂了个 `_start` 的牌子。链接器找不到 `_startup` 时，只能随机猜一个默认入口放行。这属于极其危险的漏洞。

## 2. 核心架构设计：三轨三后端与“降级保险丝”

为了最大程度规避硬件烧毁、碰撞等风险，方案设计了极其灵活的**控制后端模式**，以及它们之间的**平滑回退（降级保险丝）链**。

```text
【安全回退链 (防灾保险丝)】
 真实动作 (real) -> 只读检测 (readonly) -> 板上模拟 (simulated) -> 彻底禁用 (disabled)
     ^                                                                   ^
     |                                                                   |
  【现场最激进状态】                                                 【物理保底状态】
 (抓取、抬升、180°放)                                               (完全不碰串口、纯前端拿保底)
```

### 2.1 机械臂控制的四种“后端模式”

1.  **彻底禁用 (disabled) —— 【默认自保级】**
    *   **大白话比喻**：**“拔掉插头，装作根本没有机械臂”**。
    *   **行为**：系统判定机械臂不可用，彻底关闭 UART2 串口，绝不向芯片外部引脚（如开发板 F12）写入任何数据，只依靠 FPGA 视频分析输出识别结果，拿初赛级别的保底分。
2.  **板上模拟 (simulated) —— 【沙盘演练级】**
    *   **大白话比喻**：**“在电脑里模拟飞行，不碰真飞机”**。
    *   **行为**：机械臂动作控制器真实运行，但数据只在 CPU 的内存里打转（Mock 角度收敛、超时、故障），不初始化外部串口，在不连接真实机械臂时，完美验证 20 轮状态机跳转。
3.  **只读检测 (readonly) —— 【睁眼瞎看级】**
    *   **大白话比喻**：**“只戴望远镜看，手插口袋不乱动”**。
    *   **行为**：允许初始化 UART2 串口，但**只被允许**向机械臂发送 `GET_ANGLES`（读取当前角度）查询指令。无条件禁止发送任何移动、使能或夹爪指令。
4.  **真实动作 (real) —— 【全负载真机级】**
    *   **大白话比喻**：**“实弹演练”**。
    *   **行为**：在操作员确认、物理加固、急停断电准备好后，才允许发送关节角度和夹爪控制指令。

## 3. 为什么“测试通过”不能烧录？当前 G1–G3 到底卡在哪？

虽然在 Host（电脑上）测试显示全部通过，但目前 G1、G2、G3 均处于 **PARTIAL（部分通过）** 状态。在进入 G4（正式烧录）前，存在以下几个**纯软件层面的 P0 级严重阻塞点**，必须由 Codex 独立在当前分支 [codex/mycobot-g0-g3-bringup-20260714](file:///d:/第十届集创赛-雄芯院材料) 上修复：

1.  **QEMU测试入口不一致（严格门禁失效）**
    *   **阻塞事实**：链接器找不到 `_startup` 入口，使用默认入口运行虽然通过了，但在板卡上运行极易跑飞。
    *   **修复要求**：统一 [scratchpad.lds](file:///d:/第十届集创赛-雄芯院材料/final_project/cpu/tests/scratchpad.lds#L3) 与 [qemu_test_startup.S](file:///d:/第十届集创赛-雄芯院材料/final_project/cpu/tests/qemu_test_startup.S#L2) 的入口符号，任何 Linker Warning 必须直接判定编译失败。
2.  **编译矩阵 3/4 缺陷（符号被回收）**
    *   **阻塞事实**：`arm_bringup + disabled`（独立自检+禁用机械臂）组合在编译时，因为没有调用 `round_controller`，导致相关符号被编译器“垃圾回收”清空，无法通过 ELF 校验门。
    *   **修复要求**：严禁放宽校验门限制！推荐为 `disabled` 模式增加 **“20轮零动作自检逻辑”**，从而在代码里显式保留对状态机符号的调用。
3.  **QEMU 测试无真实超时**
    *   **阻塞事实**：即使测试脚本指定了 `-TimeoutSeconds 15`，但如果 QEMU 进程挂死，它并不会被强制杀掉，依然会无限挂起。
    *   **修复要求**：利用 PowerShell 异步子进程管理，实现真超时终止。
4.  **构建脚本 fail-late 隐患**
    *   **阻塞事实**：构建脚本 `-BoardBuild` 总是先生成好正式的 ELF/HEX/BIN 制品，再在最后一关因为校验失败而拒绝。这很容易让操作者误用上一次残留的旧制品去烧录。
    *   **修复要求**：在生成任何正式制品前就必须 **fail-closed（提前失败并中断）**，切断所有带病制品的输出。

## 4. 官方协议核心收紧：到位全靠回读，TX不等于动作完成

我们通过复核 Elephant Robotics 官方串口协议，彻底打破了“盲目等待机械臂状态”的幻想：

*   **发送 0x22 (角度) / 0x66 (夹爪) 没有任何应答**：
    字节发出去仅仅代表“串口发送成功”，不表示机械臂已经收到或运动到位。
*   **唯一合法的到位判定**：
    发送动作指令后，必须立刻转为 **Single-flight（单发单收）** 机制，向机械臂发送 `GET_ANGLES (0x20)` 并通过查询 `IS_MOVING (0x2B)` 辅证。只有当读回的角度与目标角度的差值连续收敛在允许的软容差（如 $\le 3^\circ$）内时，才能把状态机推向 `ARM_STATE_DONE`。
*   **夹爪确认策略**：
    发出夹爪控制后，必须轮询 `IS_GRIPPER_MOVING (0x69)` 确认运动停止，然后再读取 `GET_GRIPPER_VALUE (0x65)` 确认读数稳定。

## 5. Codex 协同分工：什么时候你需要亲自“拉电闸”？

根据 [mycobot_cpu_board_bringup_implementation_plan_20260714.md (line 181-202)](file:///d:/第十届集创赛-雄芯院材料/final_project/docs/technical_plans/mycobot_cpu_board_bringup_implementation_plan_20260714.md#L181-L202) 的规定，团队成员与 Codex 之间有非常明确的安全职责边界：

### 5.1 Codex（AI 助手）独立关起门来做的（G1.5–G3.5）
*   **内容**：在不碰任何硬件、不烧录、不连 J52 信号线的前提下，修改代码、修复编译 Warning、跑通严格的 QEMU 超时机制，确保 RISC-V 矩阵 4/4 严格 PASS，并形成只读的 `simulated ELF` 审查包。
*   **状态**：这一步完全由 Codex 在新会话的下一步里独立完成，**在此之前用户不需要连板子**。

### 5.2 用户（你）必须在现场亲力亲为的硬动作（G4 起）
*   **G4（SoC部署）**：在 Efinity GUI 界面里生成正式的 `soc.h` 和约束文件，并将生成的 linker、startup 放进受控目录，配合执行 `git status` 审查。
*   **G5（首次板上模拟）**：**必须断开 J52 机械臂接线（Pin4悬空）**。由用户执行烧录，并观察开发板 UART0 日志是否输出自检 banner，使用逻辑分析仪确认开发板 F12 引脚处于静默状态。
*   **G8（真实臂只读）**：用户负责**在断电状态下**完成机械臂与开发板的接线，确认机械臂独立 12V 供电。手动开机后执行只读命令测试，**手按在总电源开关上，随时准备拉闸**。
*   **G10（首次真实动作）**：完成机械臂物理加固、清场，并在现场安全员的盯防下，执行受控的低速 `HOME -> home_ready` 极简动作。**一旦机械臂发生抖动、撞击、方向跑飞，必须在 1 秒内切断 12V 物理供电**。

*   **截止时间（Dead-line）**：
