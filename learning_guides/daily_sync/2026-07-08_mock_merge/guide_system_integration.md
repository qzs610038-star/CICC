## 1. 今日最核心的改动与经验

在系统集成测试与回归验证中，如何通过设计**“全局异常捕获”**保护物理实体硬件，以及如何**“如实记录和应对测试中的未覆盖路径”**，是今日最核心的系统工程经验。

### 📌 核心点一: EOF 与 Ctrl+C 全局捕获下的舵机紧急释放 (硬件安全)
* **改动背景与问题**：
  在 `run-23` 的自动化测试中，由于管道输入 stdin 耗尽，导致进程抛出 `EOFError` 异常强行终止。由于终止过程没有经过释放命令，六轴机械臂的舵机一直处于上电锁死悬空状态，导致舵机急剧发热并伴随跌落损毁风险。
* **源码剖析**：
  在 [teach_replay_pick_return_ready.py:L2194-L2214](file:///d:/第十届集创赛-雄芯院材料/mycobot_pc_tests/teach_replay_pick_return_ready.py#L2194-L2214) 中：
  - 无论是因为 `input()` 被强制截断抛出 `EOFError`，还是用户按下 Ctrl+C 触发 `KeyboardInterrupt`，最终都会进入 `finally` 代码块。
  - `finally` 中严格执行 `release_all_servos`，切断舵机动力，使机械臂处于可手动挪动的“松弛”安全状态。
* **经验总结**：
  在涉及物理执行器的系统中，“异常退出必释放物理动力”是绝对的安全红线。

### 📌 核心点二: 未触发分支（V2.12 Retry）的如实风险记录与实验设计
* **改动背景与问题**：
  虽然 v2.12 引入了三段式判定以解决 sync 返回 0 假失败的缺陷。但在今日的 `run-25` 回归测试中，系统跑出了 100% 的 Happy Path（没有进任何兜底分支）。这导致新写的 post-failure 和 retry 代码**在运行时根本没有被触发过**。
* **源码剖析与风险**：
  由于该路径在实测中未触发，其实际运行正确性没有独立背书（即所谓的“代码逻辑正确，运行时未覆盖”）。
* **经验总结**：
  在系统集成报告中，**必须如实标注该风险，不得将“未触发的代码”宣称为“已实测验证”**。

## 2. 可迁移的系统级工程经验

* **避坑警示**：
  后续在板上 CPU (C 侧) 移植时，C 语言不具备 Python 的 `try-finally` 机制。作为集成负责人，C 必须要求并复核：**当 CPU 发生致命错误（如 hardfault、复位或跳出主循环）时，是否有硬件看门狗或特定中断服务函数去主动释放机械臂的扭矩（使之变软）**。
* **通用方法论**：
  **测试证据链的严密性**。任何系统级稳定性结论（例如“5次抓取 100% 成功”），都必须附带其对应的日志文件名、提交 ID 和 commit 状态。严防口头承诺，一切以日志证据为准。

--- 3. 推荐自行学习的相关知识

* **推荐自学点 1**：**软件测试中的“故障注入（Fault Injection）”方法**
  * **为什么学**：为了在正式移植前彻底验证 v2.12 的 retry 分支在板上 CPU 的正确性，我们不能只靠碰运气等待“假失败”发生，而需要进行主动的故障注入测试。
  * **学习切入点建议**：阅读如何通过修改 C 代码中的串口返回模拟野值、或者故意用不匹配的波特率制造偶发校验错误，观测系统是否会正确报警并执行低速重试。
