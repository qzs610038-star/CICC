## 1. 今日最核心的改动与经验

今日合并的核心改动重点规范了识别系统与控制系统之间的“安全红线”，并在板上 CPU 侧引入了多重快照校验，防止在高速数据吞吐时由于时序错位产生错误决策。

### 📌 核心点一: 固定点抓取授权的安全边界确立
* **改动背景与问题**：
  在早期的讨论或初赛 demo 中，曾有试图在 FPGA 侧使用视觉坐标实时控制机械臂运行轨道的想法。这直接导致了系统的调试链路异常复杂（需要处理图像标定、坐标系映射、运动平滑等），且在大赛现场复杂的电磁和光影环境下，极易引发机械臂的“物理暴走”和碰撞损坏。
* **源码剖析**：
  - 在 [task_matcher.h](file:///d:/第十届集创赛-雄芯院材料/final_project/cpu/app/include/task_matcher.h#L455-L460) 中，移除了任何“将 `grab_center` 坐标交付给机械臂控制”的暗示。
  - 软件决策逻辑被重新理顺：CPU 的 `match_action` 输出 `GRAB` 仅代表“允许机械臂执行预设的固定点 P_pick 抓取序列”，不提供实时抓取中心坐标给机械臂做实时伺服。
  - `grab_center` 仅用于 OSD 叠加框和 UART 终端日志打印，作为调试阶段的偏差观测参考。
* **经验总结**：
  在多核或分布式联调系统中，将控制算法与识别决策解耦（采用高内聚、低耦合的动作码触发机制），是最大化系统鲁棒性并降低调试复杂度的捷径。
  > **场景比喻（安检闸机授权，自主通行）**：这是一种经典的“安检与通行解耦”逻辑：CPU 侧只充当“安全闸机”的角色，判断刷卡（属性匹配）是否成功。一旦成功，闸机给出一个“开闸放行”（`match_action=GRAB`）的简单脉冲信号。具体的走路动作（如怎么抬手、落手、握爪）完全由机械臂主控独立根据固定的最优轨道表执行，它不需要知道闸机背后的实时视频晃动坐标，避免机械臂受到偶然光影偏差的干扰。

### 📌 核心点二: `frame_id` 二次确认防冲突机制
* **改动背景与问题**：
  在 CPU 读取 FPGA 的 `LIVE_*` 寄存器特征快照（如包络框 bbox、前景面积等）时，FPGA 逻辑可能由于 CDC 时序冲突或 VSYNC 突发重合，在 CPU 读期间更新了快照区，导致读出的 bbox 最小值来自上一帧，最大值却来自下一帧（即发生读写冲突）。
* **源码剖析**：
  - 在 [board_io.c](file:///d:/第十届集创赛-雄芯院材料/final_project/cpu/app/src/board_io.c#L627-L636) 中，重构了 `board_io_read_features` 特征快照读取函数：
    在读完所有特征后，再次读取 `SYS_STATUS` 寄存器。
    验证读取前后的 `frame_id` 是否一致，且 `valid` 是否仍为真。
    如果不一致，直接废弃本次读取到的数据，返回 `-1` 并通知调用方在下一帧重试。
* **经验总结**：
  硬件锁存机制在大批量数据读取时，软件必须辅以“防覆盖”的防御性双重读数机制，从底层根绝数据脏读的发生。
  > **场景比喻（“双重曝光防虚焦”模型）**：如果你在按下相机的快门瞬间，发现镜头里有影影绰绰的影子在晃动（帧 ID 在读取期间被改写）。为了避免洗出来一张虚焦、重影的照片，你直接作废这一张，当场重新再按一次快门。这给软件读取底层寄存器加上了防冲突的硬门槛。

## 2. 可迁移的系统级工程经验

* **避坑警示**：
  在 [board_io.c](file:///d:/第十届集创赛-雄芯院材料/final_project/cpu/app/src/board_io.c#L101) 的 `board_io_commit_config` 函数中，对配置超时进行了严格报错，主循环在 commit 失败时会触发 `FATAL` 并在心跳中循环保活。根据 `STYLE_GUIDE.md` 的规范，该部分**未被运行时充分触发验证**，属于**代码审查通过、运行时未触发**分支。在物理环境联调时，一旦遇到该 FATAL，应优先排查 APB3 硬件连线和时钟状态，切勿强行屏蔽。
* **通用方法论**：
  **保守失败（Fail-Safe）**。在 `task_matcher.c` 中，当拨码开关选择的 `TARGET_SEL` 寄存器地址未被 FPGA 侧引出或不可用时，系统会自动清空目标并返回 `NONE`，不允许沿用上一次的历史目标继续抓取，从系统级阻断了机械臂“抓错”和“空抓”的退路。
