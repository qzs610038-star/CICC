## 1. 今日最核心的改动与经验

在系统级集成测试中，有两项关键的系统维护经验：如何设计**“异常捕获下的物理安全托底”**以保护硬件；以及如何**“在版本迭代中客观、如实地归档测试风险”**。

### 📌 核心点一: EOF 与 Ctrl+C 下的六轴电机主动松弛 (硬件应急保护)
* **直观比喻（电磁锁保护模型）**：
  就像大楼的门禁电磁锁，一旦发生火灾或断电（异常退出），电磁锁必须自动弹开释放（切断动力），以确保人员可以自由进出（手动挪动硬件）。
  在之前的 `run-23` 自动化测试中，由于输入管道 stdin 耗尽，进程直接遭遇 `EOFError` 瞬间终止。因为没有执行释放指令，机械臂的六轴舵机仍处于上电锁死悬空状态，导致电机急剧发热并伴随跌落断电的损毁风险。
* **源码剖析**：
  在 [teach_replay_pick_return_ready.py:L2194-L2214](file:///d:/第十届集创赛-雄芯院材料/mycobot_pc_tests/teach_replay_pick_return_ready.py#L2194-L2214) 中：
  - 无论是管道中断抛出的 `EOFError`，还是用户手动 Ctrl+C 触发的 `KeyboardInterrupt`，异常链条都会被强制导向最底层的 `finally` 保护区。
  - 在此区间内严格执行 `release_all_servos`，切断舵机扭矩，使机械臂瞬间“变软”，避免锁死和发热。
* **经验总结**：
  在涉及物理执行器的系统中，“异常退出必释放物理动力”是绝对的安全红线。

### 📌 核心点二: 未测试覆盖分支的“如实风险”归档规范
* **改动背景与问题**：
  v2.12 引入了三段式判定以解决假熔断问题，虽然逻辑非常严密，但在今日的 `run-25` 实测中，由于跑出了 100% 的 Happy Path（未发生任何到位超时），导致新编写的重试代码**在运行时其实根本没有被触发过**。
* **源码剖析与风险**：
  虽然代码通过了 Codex 的只读逻辑复核，但由于未在运行时触发，其物理行为的正确性在实测中仍属于未验状态。
* **经验总结**：
  在系统维护文档中，**必须如实标注该风险，将其归为“代码审查通过、运行时未触发”状态，严禁将未被运行时覆盖的路径直接宣称为“已实测验证”**。

## 2. 可迁移的系统级工程经验

* **避坑警示**：
  在后续将控制逻辑向板上 CPU 移植时，由于裸机 C 语言不具备 `try-finally` 机制。作为调试与系统维护负责人，C 必须在代码审查中要求：**当 CPU 发生致命错误（如 hardfault、复位或跳出主循环）时，必须通过硬件看门狗或特定中断服务函数去主动释放机械臂的扭矩（使之变软）**。
* **通用方法论**：
  **测试证据链的严密性**。任何系统级稳定性结论（例如“5次抓取 100% 成功”），都必须附带其对应的日志文件名、提交 ID 和 commit 状态。严防口头承诺，一切以日志证据为准。
