## 1. 今日最核心的改动与经验

今日合并的改动彻底攻克了机械臂到位判定的“提前假收敛”以及由于固件死区引发的“假熔断”问题，为后续 CPU 端的控制逻辑移植树立了严格的规范。

### 📌 核心点一: 二次读数确认机制 (解决到位前惯性晃动假到位)
* **直观比喻（刹车振荡确认模型）**：
  就像坐公交车，司机刚一踩刹车，车身会由于惯性前后晃动。如果在车身第一次晃过“停止线”的那一瞬间就判定车停稳了，乘客下车就会摔倒。
  机械臂在高速运动到目标点（如 `pick_hover`）时同样存在减速晃动。如果只读取一次关节角度并判断在容差范围内，很可能只是在震荡周期中恰好擦过了阈值边缘（假到位），此时如果夹爪立刻下探，就会抓偏。
* **源码剖析**：
  在 [teach_replay_pick_return_ready.py:L973-L1025](file:///d:/第十届集创赛-雄芯院材料/mycobot_pc_tests/teach_replay_pick_return_ready.py#L973-L1025) 中，通过 `confirm_count` 过滤此瞬态晃动（`ASYNC_SHORT_CONFIRM_COUNT = 2`）：
  - 必须**连续 2 次**读取到的关节角度差值都在容差范围（`ANG_STABLE_TOL = 3.0°`）内，才确认为真实停稳。
  - 过程中允许偶发的单帧 None 读数，但若差值超限，计数立刻清零重排。
* **经验总结**：
  拒绝单次判定，引入“时序连续性确认”是滤除控制实体物理惯性晃动最有效的手段。

### 📌 核心点二: 软超时后的 sync 兜底三段式判定 (解决假熔断)
* **直观比喻（分级应急退路）**：
  当家里的保险丝断了，我们不应该立刻给整个大楼拉闸断电，而应该先复查是否是瞬时超载，或者重新推闸尝试，最后实在不行再彻底断电。
  在 `run-23` 测试中，系统在 Step 9 时由于固件判定死区（在残差 $\sim 2^\circ$ 时可能返回 0），系统直接引发全局强熔断进程终止。
* **源码剖析**：
  在 [teach_replay_pick_return_ready.py:L1031-L1091](file:///d:/第十届集创赛-雄芯院材料/mycobot_pc_tests/teach_replay_pick_return_ready.py#L1031-L1091) 中设计了“有界三段式退路”：
  1. **主路放行**：`res == 1` 表示安全到位，正常放行。
  2. **支路软通过（post-failure 复读）**：若 `res != 1`，立刻复读当前角度/坐标，若误差在软容差内（角度差 $\le 3.0^\circ$），仅警告，不熔断放行。
  3. **末路重试与硬熔断**：若超限，重发一次低速关节指令（`speed=8`），再复读，若仍超限，最终执行硬熔断，切断舵机动力保护。
* **经验总结**：
  分级处理异常，给系统以自我纠偏的“缓冲带”，能大幅度提高自动化流程的连贯性。

## 2. 可迁移的系统级工程经验

* **避坑警示**：
  在板上 CPU 侧，**串口轮询节拍规范化（50-100ms 间隔）属于防溢出的工程规范，但不得在移植文档中将其标注为“修复 run-23 熔断的根因”**。根据 Codex 复核裁定，run-23 熔断的根因优先级是“固件到位判定假失败”而非“串口溢出”（日志未见串口异常文本，证据弱）。
* **通用方法论**：
  **有界与非阻塞控制**。裸机 C 语言没有 Python 的 `try-except` 异常捕获机制，因此在与 myCobot 通信的高频状态机中，所有等待循环必须包含有界计数器或定时器超时，坚决避免无条件阻塞的 `while` 死循环。

* **优先赛方资料**：
  * **推荐学习内容**：查阅仓库内 `例程/RISC-V例程/` 下关于 **“UART 串口驱动与接收中断标志处理源码”**。

* **拓展基础知识**：
  * **推荐学习内容**：**环形缓冲区（Ring Buffer）与非阻塞串口接收**
  * **应用与意义**：板上 CPU 轮询节拍固定在 $50\text{ ms} \sim 100\text{ ms}$，若使用阻塞式串口读写，会严重拖慢主控制循环。掌握环形队列，实现中断中数据自动压栈、主循环非阻塞解析。
