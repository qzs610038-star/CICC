# 通用学习指南：三人团队如何正确使用 Agent

> 生成日期：2026-07-17
> 面向角色：qzs / wsc / libaoxun 全员
> 预计阅读时间：10–15 分钟
> 适用范围：以 `competition_project_single_camera/` 为当前 bring-up 主线；动态事实仍以 [CURRENT_STATE.md](file:///D:/第十届集创赛-雄芯院材料/CURRENT_STATE.md#L1-L73) 为准。

## 先记住一句话

Agent 是“会干活的工程助手”，不是项目事实的拥有者。它可以搜索、解释、写补丁、跑测试；但“当前哪个版本能烧录、哪个地址是真实 ABI、某条链路是否已经板上通过”，必须由仓库证据和团队 Gate 决定。

把 Agent 想象成一名速度很快的实习工程师：他能在十分钟内试十种办法，但如果没有明确的工作台边界，也可能把已经调好的线路拔掉。你们要管理的是实验过程，而不是盲目追求代码量。

## 1. 所有人必须掌握的四阶段工作流

### 阶段 A：方案讨论——只读，不急着改

每个任务先让 Agent 做调查，要求它输出：

1. 已确认事实：文件、commit、日志、命令和退出码。
2. 未知变量：哪些只是推测，哪些必须上板或读真实生成物才能确认。
3. 影响范围：会触及 FPGA、CPU、接口、OSD、机械臂中的哪些边界。
4. 最小实验：一次只改变一个变量，如何判断实验成功。
5. 禁止项：本轮明确不允许改哪些文件、地址、制品或接线。

推荐提问模板：

```text
你现在只做只读调查，不修改任何文件。
目标 Gate：……
请读取 AGENTS.md、CURRENT_STATE.md 和相关接口文档。
请分开列出：已证实事实、未知变量、假设、最小验证实验、禁止修改项。
不要把 Host/mock/compile-only 结果写成板级 PASS。
```

### 阶段 B：执行计划——先锁边界，再让 Agent 动手

方案通过人工确认后，再给实施 Agent 明确的“允许区”和“禁区”：

```text
目标：只推进 Gate ……
允许修改：……
禁止修改：XML / peri.xml / SDC / 顶层 / 地址 / 机械臂动作（按实际任务填写）
不得顺手重构无关代码。
完成后必须列出文件、diff、命令、退出码、warning、未验证项和回滚点。
```

如果目标描述是“把 CPU 和 FPGA 打通”“把整个系统修好”这类大句子，先拆成 CPU Hello、一个固定寄存器、一个视频快照字段等可验证小任务。

### 阶段 C：执行——小 diff、单问题、可回滚

一次 Agent 会话只处理一个主要问题。每次修改前保存：

- 当前分支和 `git status --short --branch`；
- 当前 HEAD 与目标文件基线；
- 本轮允许修改的文件清单；
- 预计验证命令与成功标准。

不要让 Agent 通过“顺手重新生成全部工程”来掩盖一个局部错误。硬件 XML、IP、约束、顶层、BSP 和产物属于原子批次；输入变化会使旧 bitstream、ELF 和板级证据失效，详见 [AGENTS.md](file:///D:/第十届集创赛-雄芯院材料/AGENTS.md#L32-L38)。

### 阶段 D：验收——让另一个 Agent 审查，但人负责采信

第二个 Agent 可以做复核，但不能用“两个 Agent 都说可以”替代证据。验收必须按证据等级写清楚：

| 结果 | 只能证明什么 | 不能外推什么 |
|---|---|---|
| 静态阅读 | 代码意图、潜在路径 | 运行时正确 |
| Host/mock 测试 | 软件逻辑和负例 | RISC-V、MMIO、板级输入 |
| compile/link/ELF 审计 | 构建和加载布局 | CPU 已取指、UART 已输出 |
| Efinity Map/PNR/STA/CDC/bitstream | 本批次离线硬件制品 | USER2、CPU、视频、机械臂 |
| 串口/寄存器/板测原始记录 | 对应硬件 Gate | 其他未测试链路 |

当前快照明确写着 `USER2`、CPU 取指、UART0 Hello、APB 实读和 CPU→OSD 仍有未验证项；学习时要把“代码审查通过、运行时未触发”当成正常而严谨的结论，而不是失败或 PASS，见 [CURRENT_STATE.md](file:///D:/第十届集创赛-雄芯院材料/CURRENT_STATE.md#L16-L57)。

## 2. 团队每天的最小同步格式

每个人结束一轮工作后，只发下面五行：

```text
负责模块：
今日新增事实：
本轮实际验证：命令 / 设备 / 时间 / 结果
仍未证明：
等待队友的输入：文件 / 接口 / SHA / 操作
```

“我改好了”“应该能跑”不算同步。真正有用的是“我需要 libaoxun 提供同一批次的 `soc.h` 和完整 SHA”“我需要 wsc 确认 CPU 读取的字段语义”。

## 3. 合并前后必须做的五问

1. 谁拥有这个文件或事实？
2. 这个修改改变了哪个接口、时钟域、地址或安全门？
3. 旧证据是否因此失效？
4. 最小可重复验证是什么？
5. 失败时能否只回滚本轮补丁？

涉及跨子系统、XML/SDC、AXI/CDC、APB/OSD 或机械臂的变更，必须进入 Codex Review Gate；职责来源与合并步骤见 [BRANCH_MERGE_GOVERNANCE.md](file:///D:/第十届集创赛-雄芯院材料/docs/merge_governance/BRANCH_MERGE_GOVERNANCE.md#L19-L119)。

## 4. 全员必学的最小知识集

- **接口**：API 是“调用方式”，ABI 是“二进制层面的地址、布局和调用约定”，协议是“双方如何按帧交谈”，寄存器表是“硬件能读写什么”。
- **状态机**：系统不是一段从头跑到尾的脚本，而是若干状态、事件、超时和安全转移。
- **证据阶梯**：测试结果只能证明所在层级，不能跨层级宣称系统闭环。
- **Git 基线**：分支是实验台，稳定基线是封存的样机；不要把两者混成一个 `main`。
- **安全门**：未知地址不读、未知电气条件不接、未知动作不发、失败不自动扩大范围。

## 5. 十分钟自测

如果你能回答下面五题，才算掌握本指南：

1. `182/182` Host 测试通过后，哪三件事仍未被证明？
2. 为什么修改 `mem_test.peri.xml` 后不能沿用旧 ELF 和旧板测记录？
3. “UART0 115200 Hello”为什么不能证明“myCobot UART2 1000000 可用”？
4. 一个 Agent 建议改三个子系统时，你先要它补充什么？
5. 合并后你要给队友留下哪些证据，而不是只留一个 commit？

答不出时，回到 [operations_runbook.md](file:///D:/第十届集创赛-雄芯院材料/docs/agent_context/operations_runbook.md#L1-L18) 和 [STYLE_GUIDE.md](file:///D:/第十届集创赛-雄芯院材料/learning_guides/STYLE_GUIDE.md#L7-L35) 复习。

## 6. 一条底线

任何 Agent 输出都必须经过“事实—假设—验证—风险”四格过滤。它可以建议下一步，但不能替团队替换当前事实、扩大硬件权限或把未验证功能写成完成。
