## 1. 核心专有名词生动解释库

为了扫清阅读障碍，我们把交互方案中涉及的重要专有名词，用直观的比喻模型与严谨的工程定义进行对照。请点击展开查阅：

<details>
<summary>点击展开：物理与接口层名词解释 (UART / APB / CDC / T0)</summary>

### 1. TTL UART（晶体管-晶体管逻辑串口）
* **生动比喻**：**“双轨物理玩具小火车”**。TX 轨只负责运货出去，RX 轨只负责拉货回来，GND 是共同的“地基”。火车跑在 0V 和 3.3V 的电压轨道上，如果双方的地基（GND）不连在一起，火车就会脱轨翻车（电平紊乱，数据出错）。
* **严密工程定义**：一种异步串行通信物理接口。在微控制器中，高电平代表逻辑 1（通常为 3.3V 或 5V），低电平代表逻辑 0（0V）。需要通信双方共地，且逻辑电平标准必须一致，否则可能烧毁芯片。

### 2. 1 Mbps 8N1
* **生动比喻**：**“每秒跑百万箱货的超速货运列车”**。车箱规定“每次装 8 箱货，不进行货物质量安检，卸货时留 1 毫秒踩刹车”。
* **严密工程定义**：UART 的串行通信参数配置。波特率（每秒传输位数）为 1,000,000 bps（也就是每秒一百万位，要求极高的时钟稳定性）；每个字符的数据位为 8 位，无奇偶校验位（No parity），停止位为 1 位。

### 3. APB（高级外设总线）
* **生动比喻**：**“大楼内的办公辅路”**。大楼中心是大脑（CPU），边缘是各种功能部门（如 FPGA 里的寄存器）。APB 就是连接大脑和边缘部门的专用小道，CPU 可以随时通过它给边缘部门下达指令或读取他们的工作日志。
* **严密工程定义**：AMBA 总线协议族中的一种轻量级外设总线。主要用于连接芯片内部的低带宽、低功耗外设（如寄存器、GPIO、UART 等），由 CPU 作为主设备发起读写请求。

### 4. CDC (跨时钟域传输)
* **生动比喻**：**“隔洋跨时差通话”**。高铁（FPGA 跑在高速时钟，比如 148.5 MHz）上的人，想要把包裹（视频统计特征）精准抛给月台上正慢慢散步的人（CPU 运行在 200 MHz 的另一个独立时钟源）。如果两人的节奏没踩准，包裹就会掉在铁轨上摔碎（数据亚稳态导致读错）。我们需要在月台上安放一个“中间缓冲邮箱（Results CDC 模块）”来存放包裹。
* **严密工程定义**：多时钟系统中，信号从一个时钟域传输到另一个异步时钟域的现象。若不处理，可能由于目标触发器的建立/保持时间不足导致亚稳态。常用双锁存器打两拍或握手 FIFO 进行隔离。

### 5. T0 放行表 (位于 [io_pin_map.md](file:///D:/第十届集创赛-雄芯院材料/final_project/integration/io_pin_map.md))
* **生动比喻**：**“上航天飞机前的硬性安全检查单”**。包括“螺丝紧不紧”、“线路搭对没”、“紧急断电按钮好用不”等八项，全部打勾 PASS 后，飞船才准点火。
* **严密工程定义**：系统集成放行的一级物理门禁，要求机械臂底座物理固定、供电接线、共地电平、TX/RX 线序、外部急停、引脚映射等八项硬件指标必须由 A/B/C 三个方向的成员共同签字确认，任何一项 FAIL 或未知即判定为 NO-GO（不准连线）。
</details>

<details>
<summary>点击展开：控制与协议层名词解释 (round_controller / event_seq / Mock / 180°点位)</summary>

### 6. round_controller（逐轮控制器）
* **生动比喻**：**“比赛现场的严肃裁判”**。它紧紧盯着规则，监督每轮的进度。它说：“摆放！”队员放好物体。它说：“识别！”摄像头拍图。它说：“判断！”CPU 计算结论。如果它判断需要抓，才会发通知给机械臂司机；若是非目标，它会直接吹哨“跳过！”，绝对不让司机多开一步车。
* **严密工程定义**：板上 CPU 固件中的顶层状态机，负责统筹四任务演示中每轮事务的流转（摆放、识别开始、锁存结果、生成抓取指令或 SKIP 跳过、等待执行完成、复位）。它是动作请求的唯一合法源头。

### 7. arm_controller（动作控制器）
* **生动比喻**：**“听话的机械臂司机”**。它平时处于待命状态，双手离开方向盘。只有裁判（`round_controller`）发出“抓取”公文，它才会踩油门，把具体的六关节旋转指令打包发给串口线。
* **严密工程定义**：CPU 固件中负责机械臂指令编解码及状态维护的下层控制器。它负责处理 UART 物理帧的组包、重试、接收响应并向上汇报 busy/fault/ready 状态。它绝不独立做任何“抓”或“不抓”的判定。

### 8. event_seq / ACK 事务握手
* **生动比喻**：**“送快递的签字画押”**。CPU 每次发指令，都给包裹打上一个唯一的序号（比如“3号包裹”）。对方收到了必须回一句“已签收3号（ACK）”。如果 CPU 没收到 ACK，就不会发新包裹，防止把同一个动作发了十几遍，或者少发了动作。
* **严密工程定义**：在 CPU、操作员按钮或 OSD 中采用的序号确认协议。每次状态变更或动作触发带上 `event_seq` 序号，接收方必须在操作完成后返回同序号的 ACK，用于保障在多帧视频流下不发生事务重入或状态丢失。

### 9. 180° 点位
* **生动比喻**：**“投篮时的精准空心弧线”**。机械臂要抓起积木，画一道平滑完美的半圆，把它放到完全反方向（旋转了180度）、并且胳膊拉得最长（最大臂展）的地方，而且动作要轻，像轻轻放下鸡蛋。
* **严密工程定义**：根据官方分赛区决赛细则要求，目标物被夹取后必须轻取轻放到相对起点旋转 180°（允许误差 ±10°）且处于机械臂最大臂展处的台面。为避免振荡碰撞（跌落判定），必须采用示教记录的多点插值路径（Hover 点过渡）。

### 10. ARM_DISABLED / dry-run（无臂干跑目标模式）
* **生动比喻**：**“拔掉插头的模拟演习”**。把机械臂扔在一边，只让 CPU 脑子在跑。虽然没有真正的机械臂在抓，但 CPU 的裁判和司机程序照样模拟抓取、发送日志，打印“我现在假装抓完了”。这可以让程序在大脑层面完成测试，而不用担心撞坏真实的机械臂。
* **严密工程定义**：这是目标设计而非当前已实现事实。新方案将其拆为 `disabled`（机械臂不可用、零动作请求）和 `simulated`（运行真实动作状态机但使用内存 Mock，且不包含 UART2 路径）；两者都必须由构建配置、ELF 符号检查和板上 F12 静默证据共同证明。
</details>

### 交互过程分步详解：
1. **画面捕获与统计（FPGA，A轨职责）**：
   摄像头将采集到的图像传入 FPGA。FPGA 的预处理逻辑框选出目标区域（ROI），并自动累加前景物体的像素个数、边界框（bbox）和红绿蓝三通道的像素和值（`sum_r` / `sum_g` / `sum_b` / `sum_y`）。这一步是纯硬件的，速度极快（运行在像素时钟域）。
2. **跨域存入寄存器（SoC，A+B轨职责）**：
   FPGA 的统计特征在像素时钟域中产生，不能直接让 CPU 读取（时钟频率和相位不同，强读会产生乱码）。因此需要经过一个“邮箱”，即 `results_cdc`，安全降频并写入 CPU 可以直接访问的 APB 寄存器区（映射在内存地址中，如 [board_io.h](file:///D:/第十届集创赛-雄芯院材料/final_project/cpu/app/include/board_io.h) 定义的内容）。
3. **分类与任务匹配（CPU，B轨职责）**：
   CPU 主循环运行在 RISC-V 软核上，以非阻塞轮询方式运行。
   - `vision_classifier.c` 读取 APB 寄存器内的像素面积和三通道值，计算出物体的颜色（包含白色、黑色、红、黄、蓝），以及形状和尺寸。
   - `task_matcher.c` 根据当前裁判配置的任务编号（任务一至四），判定当前物体是否是我们需要抓取的目标物。如果是，输出动作允许信号；如果不是，判定不抓并抛出理由（例如“颜色不匹配”）。
4. **逐轮事务推进与控制（CPU，B轨职责）**：
   - 顶层 `round_controller.c` 是整个大脑的“主状态机”。每当操作员摆放一个物体并按下“确认”键（产生 `event_seq` 事件序号），裁判程序就会启动一次“识别—判断”。
   - 如果判断为“非目标”，裁判程序会调用 SKIP 跳过本轮动作，直接写入“跳过，因为颜色不匹配”等语义，并返回 ACK 握手，宣告本轮结束。
   - 如果判断为“目标”，裁判程序将**唯一一次**发出 `request_arm_grab` 指令给 `arm_controller.c`。
5. **机械臂司机开车（CPU，B+C轨职责）**：
   `arm_controller.c` 翻译该指令，并将预先示教好的 180° 六关节动作路径（Hover过渡点）包装为协议帧。
6. **物理串口发送（UART2，C轨职责）**：
   CPU 外设控制器将数据通过板载 UART2 以 1 Mbps 速率发出。TTL 信号经过共地线缆传给机械臂底座座舱内的控制板。
7. **抓取与显示渲染（执行，C轨职责）**：
   - 机械臂执行抓取，并在相对起点旋转 180° 且最大臂展处轻轻放置物体。
   - 同时，CPU 把识别出的结果和动作理由写回 APB 寄存器，由 FPGA 上的 OSD 模块在显示器屏幕上渲染出直白的人类语言，告诉评委系统正在干什么。

## 3. 最新方案中的关键约束与“防错门禁”

为防止团队在最后的紧张调试中烧毁硬件、甚至摔坏机械臂，[简要方案](file:///D:/第十届集创赛-雄芯院材料/final_project/docs/technical_plans/mechanical_arm_member_next_step_brief_20260713.md)中设计了**四道门禁**，必须严格按顺序“通关”：

```
【第一关: T0 物理门禁】
八项硬性安检全 PASS ──► 允许电气接线
       │
       ▼
【第二关: D2 回环监听】
无臂状态 1 Mbps 握手 100/100 帧正确 ──► 允许开启 UART 驱动
       │
       ▼
【第三关: D3/ARM_DISABLED】
只读 GET_ANGLES + 软件干跑 Mock 验证 ──► 允许将控制链接入 main.c
       │
       ▼
【第四关: D5/F2 动作分级放行】
低速空载单段动作 ──► 低速单积木 5 轮带载测试 ──► F2 比赛最终放行
```

### 约束 1：物理防烧约束（T0 放行表）
* **为什么要对齐**：开发板、电平转换模块与机械臂都是通过导线硬连的。在现场，如果引脚号打错、线序接反（TX 错接电源线）、或者供电共地阻抗不一致，**上电的瞬间开发板或机械臂的串口收发器就会烧毁。**
* **如何体现在开发中**：在 [io_pin_map.md](file:///D:/第十届集创赛-雄芯院材料/final_project/integration/io_pin_map.md) 未由三名成员（A-FPGA负责人、B-CPU负责人、C-机械臂负责人）完成全部八项硬性指标（电平、地线、急停等）核对并签核前，**严禁物理接线，禁止使用真实机械臂当串口调试线。**

### 约束 2：不乱开枪约束（禁止 matcher 直通机械臂）
* **为什么要对齐**：视频是一帧一帧进来的。如果把分类器 `task_matcher` 的输出直接连在 `arm_controller` 上，摄像头只要对着积木，**CPU 就会在 1 秒内连续发送几十次“抓取”命令，直接导致机械臂在半空中疯狂抽搐、电机烧毁甚至跌落。**
* **如何体现在开发中**：禁止把 matcher 直接挂钩机械臂。只有在 `round_controller` 收到操作员触发（有唯一的 `event_seq`），锁定本次识别结论后，触发了“单次请求逻辑”，才允许发出一份动作请求公文。而且第一版必须默认定义 `ARM_DISABLED` 宏在干跑下测试，只有干跑时 20 轮“非目标轮不发送任何动作请求，目标轮仅且只发送一次动作请求”完全合格后，才允许向下一步迈进。

### 3. 串口回环与只读先验（D2 与 D3 门禁）
* **为什么要对齐**：软件发出去的数据如果波特率不准（例如时钟分频不对，把 1M 跑成了 9600），机械臂要么毫无反应，要么乱动。
* **如何体现在开发中**：
  - **D2 无臂验证**：断开机械臂，用一条导线把开发板的 UART2 TX 和 RX 短接（或者接逻辑分析仪）。CPU 发送 100 帧协议包，如果自己在 RX 接收端能 100% 不丢字节地完整收回，才证明 CPU 串口驱动没有大碍。
  - **D3 真实臂只读**：接上真实的机械臂，但 CPU 此时只发送 `GET_ANGLES`（获取角度命令，只读），不发送任何运动命令。连续 30 次正常返回且没有发生串口超时，才说明两端电气和电平是畅通的。

### 4. 决赛 180° 抓放与底座物理固定约束（F2 放行门）
* **为什么要对齐**：
  - 官方规则极其苛刻：放置物体时不仅要旋转 180°，还要在最大臂展处。最大臂展意味着机械臂的物理力矩是最大的。如果底座只是松松垮垮地用塑料扣扣在乐高积木上，**机械臂猛地一甩，整个底座都会歪掉甚至翻倒。**
  - 底座一旦产生 1 毫米的肉眼难察位移，在最大臂展端的抓取误差就会放大成数厘米，导致后面的积木全部抓不稳、在台面上滑落（跌落判定，全项不得分）。
* **如何体现在开发中**：
  - 机械臂成员（C轨）必须用乐高多点紧固，并在桌面上设置物理标线（外部基准）。每次动作完检查底座有没有发生位移。
  - 在动作放行上实行两级走：第一级（D5门）只放行低速、空载、单段的 `Home -> home_ready` 运动。第二级（F2门）使用单一已验证的 2cm 正方体进行至少 5 轮低速带载抓放测试。如果在这个过程中底座没有位移、没有未夹稳、没有提前释放或跌落，且全程有录像证明，才能由 Codex 批准并在生产构建中关闭 `ARM_DISABLED` 宏，把动作机制正式合入决赛构建。
