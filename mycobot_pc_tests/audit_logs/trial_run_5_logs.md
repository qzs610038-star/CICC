## 4. 本次（第五次）实验异常根因分析 (来源: Gemini)

### 4.1 异常现象
在执行步骤 3（短距离直线下探到 `pick`）时，程序依然瞬间抛出异常 `pick: 短距离直线动作超时或失败 (返回 0)`，导致流程熔断。

### 4.2 深度根因分析
*   **代码修改确认**：虽然在第四次实验后，我们尝试将 [checked_short_linear()](file:///d:/第十届集创赛-雄芯院材料/mycobot_pc_tests/teach_replay_pick.py#L298) 里的底层坐标指令的 `mode` 从 `1`（直线插值）修改为了 `0`（关节空间插值）：
    ```python
    res = mc.sync_send_coords(target_coords, speed, 0, timeout=timeout)
    ```
    但这只是将运动路径生成策略从直线变成了关节插值。
*   **黑盒 IK 解算的致命限制**：
    在 `pymycobot` 的底层 API 中，`sync_send_coords` 的接收参数是三维空间坐标（X, Y, Z, Rx, Ry, Rz）。**只要下发的是坐标，固件端就必须启动逆运动学（IK）解算**，将这组笛卡尔坐标转换成 6 个关节的驱动角度。
    *   在本次实验中，`pick` 点处于臂展较长且高度较低的极限位置（$X=156.1, Y=-185.8, Z=70.7$）。
    *   在下探的过程中，虽然终点关节角 `angles = [-35.59, -62.49, -75.93, 46.66, 4.13, 98.78]` 是完全合法且可达的（因为这是手动示教读出来的），但在将 `[156.1, -185.8, 70.7, 176.37, -2.42, 135.62]` 这一组笛卡尔姿态目标输入到固件内置的 IK 求解器时，由于存在姿态多解、或者处于求解边缘，**固件自身的解算器极易发生解算失败或溢出**。
    *   一旦固件 IK 求解失败，它甚至不会尝试启动运动，直接向串口返回代表失败的 `0`，从而瞬间导致上层 Python 抛出动作失败的 RuntimeError 熔断。

## 5. 下一步重构建议 (来源: Gemini)

为了彻底根除 myCobot 官方固件在笛卡尔坐标控制（IK 解算）上的不稳定性，最本质、最可靠的修复方案是**在回放运动中完全废除坐标控制，全闭环改用关节角度（Angles）进行运动驱动**：

### 5.1 彻底抛弃坐标驱动
由于我们在手动示教阶段已经**同时且精准地**记录了每个示教点的关节角（`angles`）和空间坐标（`coords`），回放时直接使用 angles 驱动是唯一能保证 100% 物理可达的方案。
*   将 `checked_short_linear()` 彻底废除或改写为 `checked_short_angles()`，改用关节角度同步驱动：
    ```python
    def checked_short_angles(mc, target_angles, speed, timeout, label):
        print(f"  -> 短距离关节回放到 {label}: {target_angles}")
        res = mc.sync_send_angles(target_angles, speed, timeout=timeout)
        if res != 1:
            raise RuntimeError(f"{label}: 短距离角度动作超时或失败 (返回 {res})")
        return True
    ```
*   在 `verify_coords_near` 中，我们依然保留 `coords` 读数来仅作为到位后的**一致性校验**（校验末端偏差是否在 25mm 范围内），而不让坐标参与任何的运动控制。

通过这种纯角度闭环驱动，能够彻底摆脱 myCobot 底层固件逆运动学解算失败的困扰，从根本上解决运动到 pick/drop 点时熔断中断的硬件宿疾。
