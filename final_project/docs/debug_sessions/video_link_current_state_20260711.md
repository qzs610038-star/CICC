## Intended Architecture

```text
camera 0 MIPI CSI -> RAW10 (40-bit / 4 pixels per clock) -> RAW8 truncation
                  -> framebuffer @ DDR 0x0000_0000 -> Debayer -> CDC bridge
                                                                       |
camera 1 MIPI CSI -> RAW10 (40-bit / 4 pixels per clock) -> RAW8 truncation
                  -> framebuffer @ DDR 0x0180_0000 -> Debayer -> CDC bridge
                                                                       |
                                            SW4 HDMI-only selection -> HDMI -> PC
```

- Two framebuffer writer channels are configured through the existing
  two-input AXI interconnect (`S_COUNT=2`).
- Camera 0 uses DDR base `0x0000_0000`; camera 1 uses `0x0180_0000`.
- SW4 (`i_sw[1]`) selects only the HDMI-facing channel mux. It must never gate
  either CSI receiver, framebuffer writer, AXI write path, or DDR address.
- On reset, `channel_sel=1`, so HDMI defaults to camera 1 (ch1). A stable SW4
  press toggles ch0/ch1. LED19 indicates ch1 is selected.
- The CPU must eventually read compact per-frame features through the SoC
  register interface. CPU software must not treat the framebuffer addresses
  above as a final CPU-visible ABI until generated `soc.h` and cache policy are
  locked.

## Code State

### Camera and display RTL

The following are in the active `top.v`:

- Two `soft_mipi_rx_top` instances, one per camera.
- Raw conversion assumes RAW10 packed as 40 bits / four pixels and converts to
  32-bit RAW8 before each framebuffer.
- Both framebuffer channels exist. The ch1 writer was corrected to use
  `rx_out_de1` and `ch1_raw8_4pix`; it is no longer tied to constants.
- Each channel has a `video_2pix_to_1pix_cdc` bridge. The current parameters
  are `FIFO_DEPTH=4096` and `START_LEVEL=256`.
- HDMI selects from the ch0/ch1 CDC outputs. Its ready logic also selects from
  the active channel rather than always requiring ch0 activity.
- SW4 debounce requires a stable new input level for a 20-bit counter interval
  (approximately 7.5 ms at the stated 140 MHz HDMI clock).

The project contains deliberate debug additions in the top level and camera
I2C modules. They are working-tree changes, not a clean release baseline.

### CPU and feature-processing state

- CPU source is no longer an empty loop: `cpu/app/src/main.c` contains a
  two-camera feature-read/classify/filter/ack control flow.
- `cpu/app/include/bsp.h` explicitly labels peripheral addresses as provisional.
  Final MMIO base addresses must be generated by the final SoC build and taken
  from `soc.h`.
- A feature-register/CPU integration plan exists separately at
  `docs/technical_plans/fpga_vision_preprocess_execution_plan_20260711.md`.
- FPGA-side ROI/statistics/feature-register hardware is not confirmed as
  complete or board-validated by this video-link session. Do not claim CPU

## Board Evidence and Current Fault Boundary

### Confirmed

1. HDMI physical output and PC display path work: both the project and vendor
   demo generate visible fallback patterns.
2. The vendor demo's HDMI input is already hardwired to its second camera path
   (`wb1_*`, equivalent to ch1). There is no button required to select camera
   input in that demo.
3. The responsive sensor control port is ch1:
   - ch0 final read address phases NACKed.
   - ch1 write device address `0x60`, register address bytes, and repeated-start
     read address `0x61` ACKed.
4. The ch1 `0x0100` read returned `0x61`; its stream bit (bit 0) is high. A
   full-byte equality check against `0x01` is not a valid failure criterion.
5. Camera 1 is now the default HDMI selection and has its real CSI output
   connected to its framebuffer writer.
6. Parsed ch1 CSI data-enable (`rx_out_de1`) has not been observed in the last
   recorded board state.
7. The official vendor demo also remains in its fallback pattern, described by
   the user as full-screen colors that change over time. Vendor `hdmi_top`
   deliberately emits this pattern whenever its input-frame stability check
   fails. It is not camera video and not an HDMI channel-selection state.

### Active Fault Boundary

The active boundary is after ch1 stream-on/I2C control and before stable parsed
CSI video:

```text
ch1 I2C stream-on acknowledged
    -> camera MIPI LP state / LP-to-HS transition
    -> DPHY HS recognition and byte clock
    -> receive FIFO activity
    -> CSI packet parsing (`rx_out_de1`)
```

Until `rx_out_de1` appears, do not prioritize changes to framebuffer reads,
Debayer, CDC tuning, HDMI formatting, SW4 selection, or CPU frame access.

The cause is not yet proved to be a specific hardware component. The evidence
is compatible with ch1 MCLK/reference clock, reset release, sensor supply,
MIPI lane/connector/board-side PHY, or a sensor/module register-table mismatch.
I2C ACK alone does not validate those high-speed/video conditions.

## Current Diagnostic Build: Iteration 108

`top.v` currently maps LED18-33 as follows. The MIPI events are sticky after
stream-on so they remain visible until reset.

| LED | Meaning when on |
|---|---|
| 18 | DDR configured |
| 19 | HDMI selects ch1 |
| 20 | global reset released |
| 21 | ch1 I2C post-reset delay complete |
| 22 | ch1 stream-on transaction complete |
| 23 | ch1 `0x0100` read complete |
| 24 | ch1 `0x0100` readback bit 0 is set |
| 25 / 26 | current ch1 clock-lane LP_P / LP_N |
| 27 / 28 | current ch1 data-lane0 LP_P / LP_N |
| 29 | LP state changed after stream-on |
| 30 | HS enable or termination seen after stream-on |
| 31 | recovered ch1 byte clock seen after stream-on |
| 32 | ch1 receive FIFO nonempty/read seen after stream-on |
| 33 | parsed ch1 CSI DE seen |

Interpretation:

- LED24 on, LED25-28 indicating LP11, LED29-33 off: the sensor is controlled
  but does not request HS output. Investigate sensor clock, supply, reset,
  connector and module hardware before more downstream RTL changes.
- LED29 on, LED30 off: LP activity occurs but DPHY does not recognize HS.
- LED30 on, LED31 off: HS is recognized but byte clock is not recovered.
- LED31 on, LED32 off: byte clock exists but no data reaches the receive FIFO.
- LED32 on, LED33 off: data reaches the receiver but CSI packet parsing fails.
- LED33 on: return to ch1 framebuffer, DDR read, CDC and HDMI-ready analysis.

## Vendor Demo Meaning

The vendor demo uses its ch1 `wb1_*` path as HDMI input. Its `hdmi_top` selects
the live input only when `vid_info_det` declares stable frames. Otherwise its
internal `color_bar_rgb` with `TEST_MODE=2'd1` emits whole-screen colors that
rotate over time.

Therefore a rotating full-screen color display after flashing the vendor demo
means HDMI output works but no stable ch1 frame reaches its HDMI stability
detector. It does not demonstrate a camera-display switch that can be toggled.

## Hardware Diagnosis Status

The user reports swapping camera hardware without an effect. This is useful but
not alone sufficient to assign blame unless the swap procedure and interface
location are recorded precisely.

To close hardware attribution, use one known-good component/board as a control:

1. Put a known-good same-model camera and known-good flex cable on current ch1.
   If it still fails while ch1 remains the response location, suspect board-side
   MCLK, reset, supplies, connector, lane routing or PHY.
2. Put the suspect camera on a known-good compatible board/interface. If it
   fails there too, suspect the camera module or module variant.
3. On current board, use a multimeter for documented camera supply rails and a
   scope for MCLK and reset at the camera connector. Do not use a normal probe
   on high-speed MIPI lanes unless an appropriate high-impedance/differential
   probing method is available.

## Do Not Repeat Without New Evidence

- Do not force HDMI back to ch0: ch0 I2C address phases did not ACK.
- Do not re-disable the ch1 framebuffer input; it must remain connected to
  `rx_out_de1` and `ch1_raw8_4pix`.
- Do not use full `0x0100 == 8'h01` equality as the stream-on verdict.
- Do not reintroduce strict I2C ACK/retry/stop scheduling that previously
  regressed observed MIPI activity. The current scheduler follows the
  completion-based reference behavior.
- Do not modify `constrain.sdc`, `mem_test.xml`, `.peri.xml`, or CSI IP
  `settings.json` as a speculative camera fix.
- Do not hardcode framebuffer addresses into CPU application code as final
  MMIO/DDR ABI.
