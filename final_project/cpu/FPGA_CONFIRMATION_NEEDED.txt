================================================================================
  [B] roi_pixel_count 的准确定义 — 阻塞 SUM_RGB_AVAILABLE 开关
================================================================================

CPU 侧理解: roi_pixel_count = ROI 内通过亮度门限(luma_th)的有效像素数。
即 "参与 sum_r/g/b/y 累加的像素数"。

CPU 用 sum_y / roi_pixel_count 直接得到 ROI 内有效区域的亮度均值，
用于白/黑判定。这要求 roi_pixel_count 和 sum_y 统计的是同一组像素。

如果 roi_pixel_count = ROI 内全部像素数（含过暗/过亮被排除的），
则 sum_y / roi_pixel_count 会被暗像素拉低，白/黑判定不准。

  FPGA 队友请回复:
  □ roi_pixel_count = 通过亮度门限的有效像素数（和 sum 同一组像素）
  □ roi_pixel_count = ROI 内全部像素（含被排除的）→ CPU 需额外处理
  □ other: ________

================================================================================
  [C] status 位定义确认 — 阻塞 STATUS_AVAILABLE 开关
================================================================================

CPU 侧预设的 status 位定义（board_io.h feature_snapshot_t 注释）:

  bit [0]  empty_foreground   ROI 内无通用前景像素 → CPU 跳过分类，返回 UNKNOWN
  bit [1]  invalid_roi        ROI 配置非法（反向/越界/空）→ CPU 丢弃本帧
  bit [2]  overflow           任一累加器溢出 → CPU 丢弃本帧 + 可上报 error
  bit [3]  dropped_snapshot   新帧到达但旧快照未被 CPU ack → CPU 性能告警
  bit [4]  roi_empty          ROI 内像素数为 0 → 同 empty_foreground，触发阻断
  bit [7:5] reserved           置 0

CPU 侧分类器入口逻辑 (vision_classifier.c classify_frame):
  if (status & 0x17) → 直接返回 UNKNOWN，不走颜色/形状分类
  阻断位: bits[4,2,1,0] = roi_empty | overflow | invalid_roi | empty_foreground
  不阻断: bit3 (dropped_snapshot) — FPGA valid/ack 协议保证快照完整性，仅作性能告警

  FPGA 队友请回复:
  □ 接受以上位定义 → 请确认
  □ 位定义需要调整 → 请给出 FPGA 侧规划
  □ 首版不实现 status 寄存器 → STATUS_AVAILABLE 暂保持 0

================================================================================
  [D] LIVE_FG_AREA 寄存器确认 — 阻塞 FG_AREA_AVAILABLE 开关
================================================================================

CPU 侧已预留:
  LIVE_FG_AREA0 = 0x0B0 (Cam0 俯视)
  LIVE_FG_AREA1 = 0x1B0 (Cam1 侧面)

语义: ROI 内通用前景像素数（基于 RGB 通道差 + 亮度门限通用前景掩码的像素计数）
约束: fg_area ≠ red_area + blue_area + yellow_area（白/黑物块不会命中颜色掩码，
      但会命中通用前景掩码）

如果 fg_area = red|blue|yellow，则白色和黑色物块填充率恒为 0，形状分类全部失效。

  FPGA 队友请回复:
  □ fg_area 首版实现，偏移如上述，语义为通用前景（不等同颜色面积之和）
  □ fg_area 首版不实现 → FG_AREA_AVAILABLE 暂保持 0，CPU 降级用颜色面积近似
  □ fg_area 偏移需调整 → 请给出新地址

================================================================================
  [E] TARGET_SEL 寄存器确认 — 阻塞 TARGET_SEL_AVAILABLE 开关
================================================================================

CPU 侧已预留:
  TARGET_SEL @ 0x06C

位定义:
  bits [1:0]  color_sel    00=通配, 01=红, 10=蓝, 11=黄
  bits [3:2]  size_sel     00=通配, 01=小, 10=中, 11=大
  bit  [4]    target_valid  0=不抓, 1=目标有效
  bits [31:5] 保留，填 0

需求:
  - target_valid 首版用拨码位（不是瞬时按键），防止误触
  - FPGA 负责物理开关同步/消抖/编码，CPU 只读稳定寄存器
  - 00 颜色/00 尺寸表示通配，不是无效
  - 形状不从拨码输入，CPU 固定 SHAPE_CUBE
  - 具体占用哪些拨码位由 FPGA 确认；i_sw[0] (复位) 和 i_sw[1] (HDMI 切换) 不可占用

  FPGA 队友请回复:
  □ 首版实现 TARGET_SEL @ 0x06C，位定义如上 → 请确认占用的物理 SW 引脚
  □ TARGET_SEL 地址需调整 → 请给出新地址
  □ 首版不实现 TARGET_SEL → TARGET_SEL_AVAILABLE 暂保持 0
  □ 拨码位不足 → 请给出可用位分配方案

================================================================================
  [H] bbox 区间语义确认 — 阻塞 top.v 集成
================================================================================

  2026-07-11 CPU 侧决定: bbox 采用半开区间 [x_min, x_max) × [y_min, y_max)。
  即 x_max/y_max = 前景像素最大坐标 + 1 (exclusive upper bound)。
  宽 = x_max - x_min，高 = y_max - y_min，无 ±1。
  对应接口冻结文档 §2.1，CPU _bbox_area() 已按此实现。

  与 FPGA 执行计划的不一致:
    FPGA plan §5.3 (line 474) 写: "推荐...bbox 输出实际命中像素的闭区间 min/max"。
    如果 FPGA 按闭区间实现，CPU 的 bbox_area、fill_ratio、中心点会系统性地
    与硬件语义差 1 个像素（对 150px 量级 bbox，相对误差 ~0.7% 但不恒定）。

  CPU 侧立场: 半开区间已写入接口冻结文档，CPU 全部测试以半开区间通过。
  如果 FPGA 必须用闭区间（RTL 实现更简单），需在寄存器桥接层做 +1 转换，
  或由 FPGA 提前告知并统一改为闭区间（此时 CPU 需要改 _bbox_area 加 +1）。

  FPGA 队友请回复:
  □ 接受半开区间，FPGA 输出 exclusive max (x_max = last_fg_pixel + 1)
  □ 必须用闭区间（RTL 原因）→ CPU 改 _bbox_area 加 +1，需提前通知
